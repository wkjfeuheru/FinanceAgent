## 任务 2:RunBudgets 收敛为单一配置源

1. `contracts.RunBudgets`:`le=` 上限从"等于默认值"放宽为全局硬上限(react_steps≤8、plan_tasks≤16、replans≤4、compliance_rewrites≤2、graph_steps≤128);新增 `from_config()` 读取 config.py 中 5 个 `ORCHESTRATION_*` 变量(当前是死配置,经此变为唯一数值源)。
2. `AdvisorSystem.__init__`:`self.budgets = RunBudgets.from_config()`,注入:
   - `_conversation_runner`:`max_steps=budgets.react_steps`(替换 run_conversation 硬编码的 4);
   - `handle_message`:`recursion_limit=budgets.graph_steps`;
   - plan 路径与合规路径经任务 3 的 profile 注入。
3. plan_execute.py:`PLAN_TASK_LIMIT`/`REPLAN_LIMIT` 改为 config 的别名(数值只在 config.py 定义一次);`validate_execution_plan` 增加可选 `task_limit` 参数;`build_plan_execute_graph` 增加 `task_limit` 参数(由根图默认 plan runner 传入)。
4. compliance.py `run_compliance` 增加 `rewrite_budget` 参数(默认取 `ORCHESTRATION_COMPLIANCE_REWRITES`);为 0 时跳过单次改写、直接 fail-closed。
5. `run_conversation`/`build_conversation_graph` 的 `max_steps` 默认改为 None→config 兜底。

验收:环境变量变更实际影响行为;达到上限时输出部分结果 + 机器可读 warning;不存在两处独立同类预算常量。

## 任务 4:P0 异步量化任务闭环

1. **契约与上下文**:`DomainTaskContext` 增加 `run_id` 字段(默认 "" 保持兼容);`single_domain_node` 与 plan `domain_worker` 填充。
2. **带上下文提交**:`compute_technical_via_gateway` 增加 context 参数;调用 `gateway.submit(..., customer_id=, thread_id=, run_id=, task_id=领域任务id)`(`CeleryQuantGateway.submit` 的 kwargs 已具备,持久化条件已具备);`AsyncJobRef.task_id` 改为携带领域 task_id(job_id 仍是 Celery uuid5);`InMemoryQuantGateway` 与 Protocol 签名对齐;收集所有已提交的 ref。
3. **pending_jobs 下传**:`OperationResult` 增加 `pending_jobs`;`_stock_research` 在 pending 时返回 refs;`domains/base.execute_node` 映射进 `DomainOutcome.pending_jobs`(字段已存在、从未写入)。
4. **pending 结论快照**:`PostgresAsyncRunRepository` 新增 `finance.pending_outcomes` 表(task_id 主键、customer_id/thread_id/run_id/conversation_id、outcome jsonb),`save/get/delete_pending_outcome`,`_ensure_schema` 幂等迁移;`AdvisorSystem.handle_message` 轮次结束时对 processing 结论按 task_id upsert 快照(best-effort)。
5. **修复真实 bug**:`project_root_state` 的 `pending_task_ids` 改为从 processing 结论的 `pending_jobs` 收集真实 Celery `job_id`——现状返回领域任务 id,而 `GET /api/runs/{task_id}` 一直按 job_id 查询,前端拿到的 id 必然 not_found。
6. **端点触发恢复**:接线 `ResumeCoordinator` + `RepositoryQuantRuntime`(resume_runner=新增 `_resume_quant_job`);`resolve_run_status(job_id, customer_id)`:
   - 归属校验(get_job_ref 已按 customer_id 隔离)→ not_found / processing;
   - cancelled → 返回 cancelled,忽略迟到成功结果,不恢复;
   - completed → 取 `gateway.result()` 指标 + pending 快照,合并进 `technical_analysis`,移除 `awaiting_quant`,重算状态,对结论跑 `run_compliance`,best-effort 把最终答复追加写回原 conversation_id,该任务无其它未完结 job 时删除快照行;返回 `{run_status: completed, response: 合规后文本, conversation_id: 真实值, task_id: job_id}`。
   - `ResumeCoordinator` 增加单任务入口 `resume_job` 供端点使用;`resume_ready` 保留供未来定时扫描(本次不实现)。
7. **取消语义**:`AdvisorSystem.request_stop` 在标记停止的同时,经 `ResumeCoordinator.cancel(thread_id)` 撤销该会话 queued/running 的量化任务(`_active_runs` 同时记录 customer_id 以便推导 thread_id)。
